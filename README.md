# next-conference

Next.JS 16 watch conference write-up 

Partial pre-rendering is the new default rendering mode for Next.js, instead of making a binary choice between static or dynamic, every route is now a hybrid. The framework first serves any UI that is not explicitly marked as dynamic. Any component that fetches data is wrapped within a <Suspense> boundary, allowing the static shell to be generated and immediately served without waiting for data to be ready. This creates fast but potentially stale characteristics, which simulates perceived performance. The dynamic content inside <Suspense> is streamed from the server as it becomes available, keeping the data fresh. 

The new “use cache” directive enhances the stability of caching behaviour by making it more predictable. This means that if multiple components on a page need the same data, the server must only fetch it once. This avoids redundant calls for data. In my own work, I have been exploring latency. My product vision requires almost instantaneous response times from the api to the client. I have enhanced latency by using a BFF architecture where Next.js handles the API call, deploying this server to the edge and making strategic use of Next.js caching features to ensure the server can respond as quickly as possible. A key part of this was deploying the serverless function to the edge, which keeps the application local to the user, cutting down network round-trip time. 

An interesting feature I will touch on briefly, is next-evals, which tracks how well next.js performs alongside certain models, currently Claude’s latest model is winning over Gemini 2.5 in terms of compatibility. Addressing concerns around vendor lock-in, Next.js recently introduced new features built around the Build and Deployment Adapters API. This feature aims to make it easier for any cloud service to support the full capabilities of Next.js. Encouragingly, this API was developed in direct collaboration with providers like AWS, Cloudflare, Firebase, and Netlify.

This move aligns with an anticipation I have, to follow the success of Next.js into a roadmap that scales beyond its own parent platform. For cross-functional teams, an adapter system could enable a more seamless and flexible flow from R&D to secure, project-appropriate production environments. Or at minimal, enhance our collaboration practices, that would ensure the right infrastructure can be decided for any project.

Next.js acts as a bridge that solves these problems. It takes the load off the client by pre-rendering pages and takes the load off the Python backend by handling caching, security, and data orchestration. It's the part that makes the entire architecture efficient, secure, and scalable for professional client demonstrations and user-facing tests. 
I believe the most effective way for us to leverage these new capabilities would be to organise a practical, hands-on workshop with Next.js. This would be an opportunity for us to explore these tools together, establish shared patterns for our R&D pipelines, and allow space to consider how to build the next generation of data driven visual user experiences at HEX. I'm keen to facilitate this and start a discussion on what we'd want to cover.

If we solely used Python for our R&D workflows, we would be limiting the front-end experience for our client showcases. Next.js, as a React Framework, allows us to capitalise on the use of a vast React ecosystem which consists of millions of pre-built components, animation libraries (like Framer Motion, React Spring), state management tools (like Redux/Zustand), and UI kits (HeroUI, Shadcn). The Python UI ecosystem is mostly limited to niche data visualisation apps such as Streamlit, not highly interactive web applications.

This setup allows front-end developers proficient in JavaScript/TypeScript and back-end developers proficient in Python to collaborate effectively on a shared concept. With abstraction libraries such as React Three Fiber, (as one example) developers can fast-track interactive demos on the client, interfacing with our powerful backend through Next.js API routes.

Next.js serves as the ideal bridge for this workflow. It’s server-side capabilities handle data fetching from our Python APIs. This frees up the client's browser from heavy operations. The benefits of this separation of concerns are clear: we enhance modularity, allowing us to re-purpose backend and front-end components in new projects and significantly increase prototyping speed without compromising on code quality. While Next.js solves significant performance, security and scalability challenges out of the box.
